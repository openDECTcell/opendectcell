## Test 1: audio with the new SETUP (5 minutes)

Since `9bfd0a4` our `{CC-SETUP}` carries no <<CODEC-LIST>> (basic speech,
which means G.726). It rang all three handsets overnight; nobody listened.

```
MAXSECS=300 EXTRA=playraw=/tmp/linlane.raw CAP=1 PUSH=linlane.raw HOLD=40 ./ringone.sh a540
```

Answer, listen ~15 s, then talk until the base hangs up.

Also check the log for `diag: {...}` lines (one per 8 s status poll, since
API 16): handle, slot, TPUI, call state, carrier, RSSI, the eight integrity
counters and the call's frame count, as one JSON object each.

| you hear | meaning |
|---|---|
| the speech sample at once, no burst | the new SETUP changes nothing for audio, as expected |
| noise or silence | the codec list mattered for the bearer after all; rerun with `EXTRA=codeclist=90020084,playraw=/tmp/linlane.raw` to confirm, and tell me |

## Test 2: a handset dials out (5 minutes)

Since API 14 our `{CC-CONNECT}` names the codec we chose when the handset's
SETUP negotiates (TS 102 527-1 §7.3.3). Never seen on hardware: it needs a
person to dial.

```
MAXSECS=120 HOLD=1 ATTACH=600000 CAP=1 ./ringone.sh a540
```

`ATTACH=600000` means it will not ring you. While the radio is up, dial any
number on the A540 (e.g. `123`) and press call. Talk for ~10 s, hang up.

| the log shows | meaning |
|---|---|
| `nwk out --> 83 07 7c 04 90 02 00 84` (or `.3 07 7c 04 ...`), digits `123` logged | the codec choice works; check the capture for your voice |
| `nwk out --> .3 07` with nothing after it | the A540 placed a basic-speech call without negotiating; fine, nothing to choose |
| the call drops right after our CONNECT | the A540 rejects our choice; tell me, keep the log |

Then the same on the C430A or AS690H if time allows.

## Test 3: register with every store loaded (10 minutes, optional)

`regall.sh` now loads the other handsets' stores during an enrolment, so their
chip slots are not cleared and they stay served. Worth one check because
registration is the path most likely to be disturbed by another handset on
air.

Re-register the AS690H (it keeps slot 3). Since `db36a17` the main link
lets only the handset the first store holds re-enrol into it, so this works,
while a different handset trying to enrol now gets "IPUI not accepted":

```
./regall.sh as690h      # PIN 0000 on the handset
```

| the log shows | meaning |
|---|---|

| the A540 or C430A turned away, or their slot cleared | the multi-store path breaks enrolment; keep the log |
| `learned the identities` into `as690h` from another handset's call | the learning gate failed again; keep the log |

## Test 7: a roamer calls a cell that does not know it (5 minutes)

Multi-cell, `docs/multicell-experiments.md` M5. A handset moving between
cells of one location area does not locate again; its first message to the
new cell is a call. Since API 19 the cell holds that `{CC-SETUP}` while it
"fetches" the record instead of turning it away. Unattended runs showed it
for the A540's automatic list access (M4 15 s, served 13 s after it was
sent). Still open: a **speech** call you dial, where a 20 s hold is
something you hear.

**First, look at the A540's display.** This morning it was turned away 120
times as a stranger (run `045732`), and it stayed silent in the runs after.
Note whether it shows the base name, "Basis nicht erreichbar"
(base unavailable), or anything unusual.

On the box (`ssh root@192.168.1.1`):

```
sh /tmp/m4.sh 2000
```

While it runs (up to 300 s), on the A540: open the call list, or dial `123`
and press call.

| the output shows | meaning |
|---|---|
| `fetch: CC-SETUP from a handset this cell does not hold`, then `fetch: CC-SETUP served at +2000 ms`, and the list opens / the call proceeds | API 19 works: a roamer's first call survives a 2 s fetch |
| `CC-SETUP served`, but the A540 shows an error | it gave up before 2 s; tell me |
| `fetch: LOCATE-REQUEST ...` first | it located first after all; still a good run, keep the log |

Then the same with `sh /tmp/m4.sh 15000`: the call should go through after
a ~15 s pause. (The A540 releases a call held 20 s with "timer expiry",
measured.) If the A540 locates first instead of calling, add

## Test 8: PINs longer than four digits (added at the bench)

GAP's authentication code is 32 bits: up to 8 PIN digits, two BCD digits
per octet, right-aligned, unused nibbles 0xF. We had only ever used `0000`.
Since API 21 the library refuses 9+ digits instead of overrunning. Re-register
the AS690H (its store is backed up in `/root/store-backup/`):

```
PIN=12345678 ./regall.sh as690h     # 8 digits: fills the AC
PIN=123456 ./regall.sh as690h       # 6 digits: tests the 0xF padding
```

| shows | meaning |
|---|---|
| registered, both times | our AC packing matches the Gigaset's for long PINs |
| `registration rejected` / handset says wrong PIN at 8 digits | the packing differs at full length (digit order) |
| works at 8, rejected at 6 | the padding differs (left vs right alignment, or 0x0 vs 0xF) |
